# Constrained query repair controller — development specification

15 October 2026. This extends the simple-chain feasibility runner. It is an engineering revision, not a novelty claim or full WebQSP parser.

## Information boundary

The runtime reads only id, raw question and split. Annotated topic IDs, parses, answer sets and proof paths remain offline. Entity names must be copied from the question; model type hints and question semantics remain uncalibrated. The runtime account cannot read the server's evaluation annotations. The official scorer is a separate command.

## Linking and planning

A small explicit operator guard rejects counting, temporal ordering, negation and superlatives. Plural set questions remain supported. Structured decoding enforces parse fields and enumerated type hints. A closed list removes generic answer-category nouns incorrectly extracted as named anchors; this rule is logged and may fail on unusually titled works.

Graph-native `/en/` keys can disambiguate a name only when name and inferred type also match. Otherwise canonical names and explicit alias fallback are queried with a sentinel row. No first-ID selection is allowed. Remaining small candidate sets receive observed descriptions and, for secondary anchors, bounded two-edge connections from an already linked primary entity. The model must choose a supplied ID or abstain. Graph IDs and names are never inferred from evaluation labels. Keys and type hints are priors, not calibrated proof of correct linking.

The primary entity's incoming/outgoing relations are enumerated in bounded pages. A capped inventory is rejected. Question-token/type lexical ranking supplies up to 32 first-step candidates; this is a restricted retrieval hypothesis space, not complete reasoning over the graph. Common relation/query lexical equivalents are declared in source. Root indices are constrained to observed candidates. The graph supplies schema metadata for selected roots. Every proposed predicate must occur in the observed roots/schema inventory.

## Restricted program and verification

The active planner chooses an index from a finite graph-derived catalog of one- and two-hop programs with equality joins to secondary named anchors. Child relations extend only in their observed schema direction. Every secondary anchor needs an observed two-edge connection matching the root. The lower-level compiler accepts up to four steps for fixtures, but the active catalog does not claim this broader coverage. All secondary anchors must be bound by a join. A compiler validates identifiers, directions, variable indices and grammar before producing SPARQL; no model-supplied executable query is accepted. It retrieves complete bounded witness rows, retaining endpoints, predicates, query index and graph snapshot. Row truncation, incomplete SQL state and transport failures never count as complete answers.

A separate model call checks question/answer type and all constraints before answering. It sees the question, linked anchor mentions, compiled program and expected type, counts and bounded samples (at most five answers and two witness rows); it does not inspect every returned row. All rows are generated by the same validated conjunctive query. This is a self-review gate with the same base model, not an independent calibrated verifier. Membership in the KG and a valid compiled join do not establish complete question semantics. Independent evaluation and trace adjudication are still necessary.

## Fixed and repair controls

Both controls share linking, lexical retrieval, schema access, first plan, compiler and final semantic gate. `fixed` permits one plan. `repair` permits at most two choices, masks previously failed programs, and supplies the first rejection/observed failure to the second choice. For an empty constrained query it acquires graph-derived join options; no gold feedback is used. Invalid arbitrary path directions are prevented by catalog construction. No gold feedback enters repair. Repeating branches without changing a failed program is not successful repair. Current controls share maximum call/token/graph budgets but can consume different realized costs; quality gains cannot be described as equal-cost gains without a separate budget analysis.

This narrow comparison tests failure-feedback plan revision. It does not test the entire proposed adaptive-acquisition method, uncertainty calibration, an external baseline, or general stopping optimality. Maximum-inference budgets and synchronous timeouts are admission/answer limits; a failing provider request can have unknown token usage. Actual usage completeness must be reported. Model timeout is 120 seconds and the wall-time admission limit 600 seconds; graph requests remain capped at 30 seconds. CPU prefill time is material.

## Scoring

`python3 -m flagship_controller.official_score PREDICTIONS EVALUATION_ONLY` uses the official WebQSP v1.0 admission, best-parse and empty-answer conventions with strict selected-slice ID validation. The prior local feasibility scorer is retained to reproduce historical JSON, not recommended for new comparisons. [Parity evidence](official-scorer-cli-parity.json) compares the downloaded, checksummed official script after only Python print syntax conversion. Train empty-answer and synthetic alternative-parse fixtures match at the official CLI's reporting precision; 36 PRF edge cases match exactly. No official test outcomes were executed for this check.

## Publication gates

Required before a final-paper claim: supported live development examples, a prospectively frozen comparison, raw traces and manifests, labeled semantic failures, support/recovery/STOP denominators, official scoring, cost-aware paired estimates, external baseline audit/reproduction, snapshot comparability assessment, a current method-specific novelty review and owner-confirmed authorship/disclosures. Quality and novelty depend on measured evidence; successful publication cannot be guaranteed by completing software tasks.
